# 大 QMT 环境能力探针

用实际运行结果确认权限，不再根据 Python 版本、模块能否导入或另一份策略的源码推断。

探针兼容 Python 3.6 语法，目标为大 QMT 内置 Python 3.6/3.12。它不查询账户或行情，不调用下单、撤单接口，不连接券商或公网。文件、SQLite、共享内存、互斥量和端口均使用独立测试对象。

## 运行

1. 在大 QMT 中创建独立测试策略，将 `tools/qmt_capability_probe.py` **完整源码**复制进去。无需填写账户号。代码顶部 `PROBE_DIRECTORY` 默认是 `F:\workbuddy-qmt-bridge-main\probe-output`；若工程放在其他位置，改为本机专用测试目录。
2. 双击 `tools/启动QMT探针配对.cmd`。保持窗口打开，看到 `[QMT-PROBE-PEER] READY` 后，立即在 QMT 中实际启动策略。配对程序默认运行 90 秒；需要更长时间可在终端运行 `python tools/qmt_probe_peer.py --seconds 180`。
3. 等待 QMT 日志出现 `[QMT-PROBE] REPORT_END`。正常配对数秒可完成；定时回调正常时，未完成项在 60 秒内结束。若定时器没有触发，60 秒后手动停止测试策略，`stop` 入口也会打印报告。不要只点语法检查；QMT 必须实际执行策略的 `init`。

配对程序使用普通 Windows Python，复用工程内的互斥量工具，因此请在完整工程中使用。它只在 `127.0.0.1:17643` 监听，并创建专用 `Local\WBQMT_CAPABILITY_PROBE_V1` 映射和对应 mutex，不打开正式桥接的映射。QMT 和配对程序须在同一 Windows 登录会话中运行。一次只运行一个同名配对程序。

端口被占用或本机连接被系统限制时，会打印具体错误；不会结束其他进程或修改防火墙。可以把两端的端口改为同一个空闲端口后重新验证。外部命令 `--port 0` 会选随机端口，仅适合同时修改 QMT 顶部 `PEER_PORT` 的用户。

## 检测内容

| 类别 | 实际操作 |
| --- | --- |
| 版本与依赖 | Python 完整版本、位数，逐个尝试 `os`、`tempfile`、`uuid`、`sqlite3`、`socket`、`mmap`、`ctypes`、`win32event`、`msvcrt` 等模块 |
| 文件与 `os` | 在唯一测试目录独占新建文件，读写 JSON/字节、`flush`、`fsync`、目录枚举、文件状态、原子重命名，以及临时文件创建 |
| 数据库 | SQLite 内存库建表/写入/提交/读取；唯一磁盘库提交、关闭、重新打开并核对内容 |
| 本机网络 | 仅回环地址的 bind/listen，以及和外部配对程序交换随机挑战值 |
| 共享内存 | 本进程创建/读写；QMT 发出本轮挑战值并收到外部进程的匹配回复 |
| 互斥机制 | 分别尝试 `ctypes` 与 `win32event`；先让外部持有同名 mutex 验证 QMT 获取超时，再让 QMT 持有验证外部获取超时 |
| QMT 调度 | 定时器注册是否接受、真实定时回调是否触发 |

Win32 mutex 的获取和释放始终在同一次 QMT 回调中完成。探针使用内部回调锁避免定时器、handlebar 和停止操作交叠；300ms 内未获得外部确认只记为配对未验证，不据此断定接口被禁。`msvcrt.file_lock` 只测试文件锁的本地操作，不能据其成功声称命名 mutex 或跨进程互斥已经成立。

## 取回报告

可写文件时，报告位于：

```text
F:\workbuddy-qmt-bridge-main\probe-output\QMT-probe-<本次编号>.json
```

不能写文件或不能导入 JSON 时，完整报告仍打印在 QMT 控制台的 `REPORT_BEGIN` 与 `REPORT_END` 之间。把 JSON 文件或这段日志提供给后续适配工作即可。报告包含环境版本、能力结果、错误类型和测试路径，不包含账户号、持仓、密钥或交易数据。

测试只独占创建带本次编号的新文件；不会打开已有数据库，不覆盖原文件。能使用 `os` 时尝试删除自己创建的临时文件及空测试子目录，保留报告。不能清理时保留这些独立测试文件并记录原因，不做递归删除。

报告 `probe_version: 2` 修复了旧版累计 120 次回调就误报超时的问题。QMT 历史回调可能在几毫秒内执行数百次；现在只按 `time.monotonic()` 的实际经过时间计算配对期限。`pair_diagnostics` 记录真实耗时、回调次数、当前阶段及等待原因，可区分共享区标记不可见、回复为空、挑战值不匹配和互斥阶段等待。

## 解释结果

- `PASS`：对应那一项实际操作成功。`import.xxx PASS` 仅表示导入，不代表相关操作可执行。
- `FAIL`：该项运行出错，保留异常类型和原因；模块不存在、路径限制、API 不可用和权限封禁是不同原因。
- `SKIP`：缺少前置条件或未完成配对，不能作为“被禁”的证据。未运行配对程序时不会把共享内存及同步机制误报为验证通过。
- `WAIT`：仍在等待配对阶段；最终报告会将未完成项转换为 `SKIP`。

文件模式主要看文件、目录扫描、原子替换、`fsync`、UUID 和签名相关操作是否通过。mmap 模式需要 `mmap.duplex PASS`，以及至少一个 `mutex.<后端>.cross_process PASS`；仅有 `mmap.local` 或 `mutex.<后端>.local` 成功不够。数据库和本机网络结果只反映 QMT 内置运行时对应操作，不应扩展为外部 Worker 的权限判断，也不证明公网访问能力。

这些结果用于确定传输与同步实现。正式报单仍需要另行验证目标柜台；本探针不承担交易验收。

接口依据：[pywin32 事件与等待接口](https://mhammond.github.io/pywin32/win32event.html)。
